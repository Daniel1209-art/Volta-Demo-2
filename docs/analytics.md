## Определения метрик (зафиксированы, менять только явным решением)

* **Метрики уровня раунда** — максимальный и средний множитель. Считаются по
  `rounds.crash_point` — глобальному крашу, одинаковому для всех игроков
  раунда. Личный множитель лампы сюда не входит.
* **RTP за окно — ФАКТИЧЕСКИЙ**: `SUM(bets.payout) / SUM(bets.amount)` по
  ставкам окна. Теоретический RTP (96.53%) — константа аудита: он вытекает из
  распределения crash-point и от периода не зависит, пересчитывать его за
  1д/7д/1м не нужно. Показывать рядом можно, считать за окно — нет.
* **Метрики уровня ставки** — решение конкретного игрока. Метрика «личный
  множитель при фиксации против финала раунда» = `bets.cashout_mult` против
  `bets.crash_point` той же строки.
* **Периоды 1д / 7д / 1м** — скользящие окна от текущего момента (24 ч,
  168 ч, 30 суток), не календарные сутки/недели/месяцы.
* **Реальные игроки** — строки с `is_bot = 0`.
* **Процент использованных переключений** = `switches_used / MAX_SWITCHES`
  (MAX_SWITCHES = **2** с 2026-08-04, до этого 4 — см.
  `lamp-switches-4.backup.md`). Бесплатное включение лампы на старте раунда
  переключение не тратит и в `switches_used` не входит. **Метрика
  несопоставима между периодами с разным лимитом**: знаменатель меняется.

## Потолки и их влияние на метрики

С 2026-08-04 в игре два потолка (`shared/engine.js`):

* **`MAX_CRASH_MULTIPLIER = 10000`** — потолок множителя раунда. Применяется
  внутри `crashPointFromHash` последним шагом (`clampCrash`), поэтому
  `rounds.crash_point` никогда не превышает `1000000`. Формула HMAC и
  provably-fair схема не изменились: потолок — clamp поверх честного
  результата, и кнопка Verify применяет ровно ту же функцию.
* **`MAX_PAYOUT_USD = 10000`** — потолок выплаты за раунд. Применяется ПОСЛЕ
  расчёта честного множителя, только к деньгам.

Что это значит для аналитики:

| столбец | потолок выплаты его затрагивает? |
|---|---|
| `bets.final_mult` | **нет** — остаётся честным, это тот же множитель, что игрок видел и может проверить через Provably Fair |
| `bets.payout` | **да** — `min(amount × final_mult, 10000)` |

Следствие: **фактический RTP (`SUM(payout)/SUM(amount)`) при срабатывании
потолка окажется ниже теоретических 96.53% — это корректно, а не ошибка.**
Расхождение между `SUM(payout)` и `SUM(amount × final_mult)` по выигрышным
строкам — это ровно сумма, срезанная потолком.

При `MAX_BET = $100` потолок выплаты начинает связывать с ×100; на истории
до 2026-08-04 (190 ставок, максимум ×13.65 / $1364.62) он не срабатывал ни
разу.

## Таблицы

### `rounds` — раунд целиком
`round_id, hash, seed, crash_point, crashed_at, client_seeds, seed_mode`

`crash_point` хранится ×100 целым; **0 означает мгновенный краш ×1.00**.
Верхняя граница — `1000000` (×10000, потолок раунда); значения выше в базе
означали бы, что потолок обошли.
`seed_mode`: `multi` — в раунде были ставки реальных игроков, их client seed-ы
вошли в расчёт; `single` — реальных ставок не было, использован системный seed.

### `bets` — итог ставки, по строке на игрока за раунд
Пишется один раз, в момент краша.

| столбец | смысл |
|---|---|
| `amount`, `payout`, `win` | сумма, выплата, выигрыш/проигрыш |
| `final_mult` | итоговый множитель выплаты (накопленный лампой `persAccum`); потолком выплаты **не** обрезается |
| `cashout_mult` | **глобальный** множитель в момент последнего OFF; `NULL` — игрок не выключал |
| `crash_point` | краш раунда, скопирован в строку: метрика «фиксация против финала» не должна ломаться, когда раунд выпадет из retention раньше ставки |
| `switches_used` | из `MAX_SWITCHES` (2 с 2026-08-04, ранее 4); бесплатный старт не считается |
| `on_count`, `off_count` | сколько включений (кроме бесплатного) и выключений за раунд |
| `had_off` | был ли хотя бы один OFF — для метрики «% раундов с хотя бы одним OFF» |
| `auto_bet` | ставка сделана при включённом автопилоте |
| `auto_switches` | сколько из переключений раунда выполнил автопилот |
| `session_id`, `is_bot` | связь с сессией; признак бот-трафика |
| `day` | календарный день в `RESET_TZ` — только для суточной «My Game History» на клиенте |

### `lamp_events` — сырая последовательность переключений
`round_id, player_id, session_id, seq, lamp_on, mult, src, at`

Пишется в момент события: порядок ON/OFF задним числом не восстановить.
`seq` — номер события внутри раунда у игрока.
Столбец назван `lamp_on`, потому что `ON` — зарезервированное слово SQLite.

**`src` — гарантии, на которые можно опираться в метриках:**

| `src` | что это | `lamp_on` | тратит переключение |
|---|---|---|---|
| `free` | автоматическое включение лампы на старте раунда | **всегда 1** | **нет** |
| `manual` | кнопка ON/OFF игрока | 1 или 0 | ON — да, OFF — нет |
| `auto` | переключение автопилотом | 1 или 0 | ON — да, OFF — нет |

`free` **никогда не бывает OFF-событием**: оно пишется в единственном месте
(`startRound`), всегда с `lamp_on = 1`, ровно один раз за раунд на каждого
игрока со ставкой. Источник, пришедший от клиента, дать `free` не может —
сервер приводит его к `auto` либо `manual`, так что подделать бесплатное
включение с клиента нельзя. `free` не уменьшает `switchesLeft` и не входит
в `bets.on_count`.

Отсюда для метрик:
* «% раундов хотя бы с одним OFF» — считать по `lamp_on = 0` (или по
  `bets.had_off`), `src` при этом не фильтровать: OFF бывает только
  `manual` или `auto`.
* «% использованных переключений» — знаменатель 4, числитель
  `bets.switches_used`; события `free` в него не входят по определению.

### `sessions` — игровая сессия, ЛОГИЧЕСКАЯ
`player_id, started_at, last_seen_at, ended_at, ip_hash, country, region, is_bot`

Несколько ws-соединений одного игрока (вкладки, переподключения) в пределах
`SESSION_IDLE_MS` склеиваются в одну строку: иначе перезагрузка страницы и
обрыв мобильной сети дробили бы «время в игре». `ended_at IS NULL` — сессия
идёт; возврат в окно склейки снимает `ended_at` обратно. Оборванные без
`close` соединения закрываются фоновой чисткой по `last_seen_at`.
Время в игре = `COALESCE(ended_at, last_seen_at) − started_at`.

## IP и гео

Сырой IP **не хранится нигде** и не покидает обработчик соединения.

* `ip_hash` = `SHA256(соль + IP)` — различает уникальных посетителей и
  повторные визиты, обратно в адрес не разворачивается. Соль генерируется один
  раз в `data/.ip_salt` (0600) или задаётся `IP_SALT`. Потеря соли рвёт связь
  со старыми хешами, игровых данных не касается.
* `country` / `region` — офлайновый CSV-диапазонник, путь в `GEOIP_CSV`
  (по умолчанию `data/geoip.csv`). Поддерживаются форматы DB-IP lite:
  `start,end,country` и city-уровень `start,end,continent,country,region,city`.
  IPv4 и IPv6 приводятся к одной 128-битной шкале, поиск — бинарный по
  отсортированным диапазонам.
* **Файла нет → `country`/`region` остаются `NULL`**, всё остальное работает.

Гео определяется по первому наблюдению сессии и при переподключении не
перезаписывается (`COALESCE`).

### Гео-база на сервере

Стоит **DB-IP IP to Country Lite** — `/var/www/volta-demo.com/data/geoip.csv`,
696 624 диапазона, ~30 МБ, владелец `www-data`. Обновляется вручную раз в месяц:

```sh
cd /var/www/volta-demo.com/data
curl -fsSL -o geoip.csv.gz https://download.db-ip.com/free/dbip-country-lite-$(date +%Y-%m).csv.gz
gunzip -f geoip.csv.gz && chown www-data:www-data geoip.csv
systemctl restart volta-backend        # таблица читается только при старте
```

Особенности этой базы:

* **`region` всегда `NULL`** — country-lite версия регионов не содержит. Столбец
  заполнится, только если положить city-уровень (6 колонок).
* **`ZZ`** — служебный код DB-IP для зарезервированных диапазонов (например,
  `127.0.0.1`). В дашборде это «неизвестно», а не страна.
* Файл вендора отсортирован не по нашей 128-битной шкале, поэтому индекс
  пересортировывается при старте: загрузка ≈3,5 с, +65 МБ RSS (замерено на
  проде: 81 МБ без базы → 146 МБ с базой).
* Лицензия **CC-BY 4.0**: при публичном использовании данных требуется
  указание источника (`IP Geolocation by DB-IP`, https://db-ip.com).

Границы диапазонов лежат в типизированных массивах, а не строками: строковый
индекс на этой же базе занимал 584 МБ RSS.

## Срок хранения

`RETENTION_DAYS` (по умолчанию 35) — окно дашборда «1 месяц» плюс запас.
Чистка раз в 10 минут удаляет `bets`, `rounds`, `lamp_events`, `sessions`
старше срока. Раньше ставки резались по календарному дню, а раунды — до
последних 600 (≈4 часа), поэтому окна длиннее суток были нерасчитуемы.

Суточный сброс «My Game History» на чистку не завязан: клиентская выборка
отбирает строки по `day = сегодня`, а не полагается на удаление вчерашних.

## Известные особенности

* **`is_bot` сейчас всегда 0** — так и задумано. Боты-заполнители стола живут только в памяти
  (`spawnBots`) и в БД не попадают, поэтому `sessions`/`bets` по определению
  содержат только реальный трафик. Флаг заведён, чтобы контракт дашборда не
  менялся, если источник бот-трафика появится позже; проставлять его надо в
  `openSession` и в записи ставки — это единственные два места.
