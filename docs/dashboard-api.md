# VOLTA — API дашборда (read-only)

Аналитический слой над схемой из [analytics.md](analytics.md). Фронтенда пока
нет — это только HTTP-контракт.

Все эндпоинты живут под `/api/dashboard/*`, отдельно от игровых, и работают
через **отдельное подключение к SQLite в режиме `readOnly`**: ни один из них
не может записать или изменить игровые данные — это держит драйвер, а не
дисциплина разработчика. Игровой цикл, генерацию раундов и provably-fair
схему этот модуль не видит.

## Авторизация

Пароль задаётся переменной `DASHBOARD_PASSWORD` в `backend/.env` (файл в
`.gitignore`, systemd подхватывает его через `EnvironmentFile`).
**Пароль не задан → дашборд отключён целиком** и отвечает `503`, чтобы
открытый доступ к аналитике не мог уехать в прод по недосмотру.

```sh
# 1. получить токен
curl -s -X POST https://volta-demo.com/api/dashboard/login \
     -H 'Content-Type: application/json' \
     -d '{"password":"…"}'
# {"token":"…64 hex…","expiresAt":1785419000000}

# 2. дальше со всеми запросами
curl -s https://volta-demo.com/api/dashboard/rtp?period=1d \
     -H "Authorization: Bearer $TOKEN"
```

* Токен живёт `DASHBOARD_TTL_MS` (по умолчанию 12 часов) и хранится в памяти
  бэкенда — **после рестарта нужно войти заново**.
* `POST /api/dashboard/logout` гасит текущий токен, `GET /api/dashboard/me`
  возвращает срок его действия.
* Пароль сравнивается по sha256-дайджестам через `timingSafeEqual`.
* Десять неудачных попыток входа с одного адреса за 15 минут → `429`. Ключ
  лимитера — хеш IP, сырой адрес не появляется и здесь.

Коды ответов: `401` без токена или с протухшим, `400` неверный период или
ключ сортировки, `404` неизвестный эндпоинт, `405` неверный метод,
`503` дашборд отключён.

## Общее для метрик

* `period` = `1d` | `7d` | `1m` — **скользящее** окно от текущего момента
  (24 ч / 168 ч / 30 суток). По умолчанию `1d`, чужое значение → `400`.
* Ответ всегда содержит `from` и `to` (epoch ms) — окно ограничено с обеих
  сторон, поэтому результат воспроизводим: раунды идут непрерывно, и без
  верхней границы повтор запроса дал бы другой набор строк.
* Доли возвращаются числом `0..1`, не процентами. Форматирует потребитель.
* Множители — обычные (`×5.00` → `5`), а не внутренние `crash_point ×100`.
  `crash_point = 0` (мгновенный краш) разворачивается в `×1.00`, иначе
  средний множитель занижался бы на каждом таком раунде.
* Всё считается по реальному трафику: `is_bot = 0`.
* Ставки фильтруются по `bets.created_at`, раунды — по `rounds.crashed_at`.

## Эндпоинты

### `GET /players`
Реальные игроки с пагинацией. `period` **необязателен**: без него берётся вся
сохранённая история (retention 35 суток).

Параметры: `limit` (1–200, по умолчанию 50), `offset`, `sort`
(`volume` | `bets` | `payout` | `rtp` | `winrate` | `playtime`, по умолчанию
`volume`), `dir` (`desc` | `asc`).

В список попадает всякий, у кого есть хотя бы одна ставка **или** хотя бы одна
сессия: зашедший, но не поставивший — тоже посетитель, у него `rtp` и
`winrate` равны `null`, а не нулю. `ipHash` и `country` берутся из **последней**
сессии игрока: адрес между визитами меняется. `playtimeMs` — сумма
`COALESCE(ended_at, last_seen_at) − started_at` по сессиям.

### `GET /multiplier-stats?period=`
`max` и `avg` глобального множителя раунда за окно, плюс `instantBusts` —
число мгновенных крашей ×1.00.

### `GET /rtp?period=`
`actualRtp` = `SUM(payout) / SUM(amount)` за окно. Рядом `theoreticalRtp` —
константа аудита (`0.9653` из [analytics.md](analytics.md), переопределяется
`THEORETICAL_RTP`). Теоретический от периода не зависит и за окно **не**
пересчитывается.

### `GET /lamp-usage?period=`
`withOff` / `withoutOff` — ставки хотя бы с одним OFF против тех, где лампа
провисела ON весь раунд. `avgSwitchUsage` — средняя доля израсходованных
переключений из `maxSwitches` (4).

Считается по колонкам `bets`, а не агрегацией `lamp_events`:
`switches_used` тождественно равен числу ON-событий с `src != 'free'`
(бесплатный старт переключение не тратит), сверено на данных прода.

### `GET /autopilot-adoption?period=`
Две **разные** величины, обе в ответе:

| поле | смысл |
|---|---|
| `withAutoSwitch` | автопилот реально дёрнул лампу (`auto_switches > 0`) |
| `withAutopilotEnabled` | ставка сделана при включённом автопилоте (`auto_bet = 1`) |
| `fullyManual` | за раунд ни одного `auto`-переключения |

Они расходятся, когда раунд рухнул раньше первой ступени плана: автопилот был
включён, а переключить ничего не успел. Первая величина мерит применение,
вторая — намерение.

`autoSwitches` — сколько событий выполнил автопилот; это ON **и** OFF, тогда
как `switches_used` считает только ON, поэтому доли одного от другого в ответе
нет: величины в разных единицах.

### `GET /personal-vs-crash?period=`
Два блока, потому что это разные вопросы:

* `cashoutVsCrash` — `cashout_mult` против множителя краша, то есть **рано ли
  игрок вышел**. Ставки без единого OFF сюда не входят (`cashout_mult` у них
  `NULL`), поэтому `bets` этого блока меньше общего.
  `avgDeviation < 0` — вышел раньше пика; `avgRatio` — какую долю пика взял.
* `finalVsCrash` — выплатной `final_mult` против множителя краша, то есть
  **сколько в итоге взял**. Считается по всем ставкам окна.
* `distribution` — `cashedOut` (зафиксировались) против `busted` (держали до
  краша и сгорели), из готового `bets.win`.

## Производительность

Индексы под фильтрацию по времени: `bets(created_at)`, `rounds(crashed_at)`,
`lamp_events(at)`, `sessions(player_id, started_at)`.
Индекс `rounds(crashed_at)` добавлен вместе с этим API — без него окно
раундов читалось полным сканом.

Предрасчёта агрегатов **нет и пока не нужно**: на момент написания в проде 631
раунд и единицы ставок, все запросы отвечают мгновенно. Строить материализацию
имеет смысл, только если по факту станет медленно, — не заранее.
